# kg/ — knowledge graph and pipeline state

What it does: stores the graph (episodes, entities, aliases, facts, edges, tasks) and the pipeline's state (runs, items, alerts) in one SQLite database, schema by numbered migrations; walks it multi-hop (neighbors, paths, timeline); resolves duplicate entities with reversible merges; and serves it to Claude read-only over MCP.
How to run it: it is a library; `kg.db.connect(cfg)` opens and migrates the database, `kg.store.Store(conn, cfg)` and `kg.state.State(conn, cfg)` read and write it, `kg.traverse.Traverser(store)` walks it, `kg.resolve.Resolver(store, state)` resolves entities.
MCP server (read-only): `.venv\Scripts\python.exe -m kg.mcp [--config OVERLAY.yaml]` from the repo root (overlay default `%APPDATA%\whispr\config.yaml`); register it with `claude mcp add whispr-kg -- <repo>\.venv\Scripts\python.exe -m kg.mcp`. Tools: `search`, `get`, `source`, `neighbors`, `paths`, `timeline`. It needs a database the pipeline has already created and migrated.
Viewer (read-only): `.venv\Scripts\python.exe -m kg.view search <text> | neighborhood <id or exact name> [options] [--config OVERLAY.yaml]` prints one JSON object (see View below).
Tests: `.venv\Scripts\python.exe -m unittest discover -s tests -p "test_kg*.py" -v`.
Config keys read: `paths.data_dir`, `kg.database`, `kg.busy_timeout_ms`, `kg.search_cards`, `kg.traverse.max_hops`, `kg.traverse.default_hops`, `kg.traverse.max_results`, `kg.traverse.max_paths`, `kg.traverse.quote_chars`, `kg.traverse.time_limit_ms`, `kg.view.*` (the viewer: `default_hops`, `max_nodes`, `svg_max_chars`, `canvas_px`, `margin_px`, `ring_px`, `start_deg`, `node_radius_px`, `center_radius_px`, `label_gap_px`, `label_chars`, `quote_chars`, `font_family`, `font_px`, `coord_decimals`, `text_indent`, `route_only_opacity`, `stroke_px.*`, `colors.*`, `palette.<entity type>`), `owner.email`, `kg.er.max_edit_distance`, `kg.er.block_chars`, `kg.er.context_items`, `kg.er.prompt`, `kg.er.schema`, `kg.models.resolve` (a `models` role, `kg_resolve`), `ontology`, `schemas.task`, `pipeline.max_attempts`, `alerts.quarantine_digest_days`, `alerts.repeat_item_runs`.
Reserved for C.5 maintenance (in config, read by no code yet): `kg.rederive_approval_usd`.

## Design

Plan: `docs/plan/C-knowledge-graph.md` §C.4–C.5, `docs/plan/D-architecture-and-ops.md` §D.1, §D.5, §D.6.

**Database.** `<paths.data_dir>/<kg.database>`, outside git. `connect` turns on foreign keys and WAL mode (readers never block a writer's COMMIT), waits up to `kg.busy_timeout_ms` for another process's lock, runs the connection in autocommit mode, and applies pending migrations in order. Writers group statements with `kg.db.transaction`, which nests through savepoints; its outermost level takes the write lock up front (`BEGIN IMMEDIATE`) and rolls back on any error, a failed COMMIT included, so the connection never stays inside a dead transaction. `fetch_one`/`fetch_all` return rows as dicts for both modules. Close the connection when done.

**Migrations** (`kg/migrations/`). `NNNN_name.sql` holds only SQL that SQLite and Postgres share: TEXT/INTEGER/REAL, TEXT ids made by code, no AUTOINCREMENT, no PRAGMA. `NNNN_name.<dialect>.sql` runs only on that dialect; full-text search is `0002_search.sqlite.sql` (FTS5), and a Postgres port adds `0002_search.postgres.sql` (tsvector) under the same version number. Each migration commits together with its `schema_version` row, so a failure leaves the previous version intact. The version row is written first, under the write lock, so two processes migrating a fresh database don't collide: the second finds the version taken and skips it. A database recording a version this code doesn't know is refused.

**Store** (`store.py`), the one data-access module for the graph:
- *Provenance root.* One episode per transcript (path, sha256, meeting time, call type, extractor version, mic coverage, output device). Episodes are tombstoned, never deleted; writing one again clears the tombstone.
- *Provenance check.* A fact or edge is `EXTRACTED` only if its quote is a verbatim substring of the transcript text passed with it; otherwise `AMBIGUOUS`.
- *Time.* Facts and edges carry `valid_from` (defaulting to the meeting start), `valid_to` and `superseded_by` + a reason. Every stored time (meeting start, valid_from/to) and every asked-for time (`as_of`, `since`, `until`) goes through `kg.db.utc_time`: any ISO-8601 offset is converted to UTC in `utc_now`'s exact format, so text order is time order (a bare date, or a time with no offset, is UTC; anything else raises `ValueError`). Supersede, never delete. Reads show active rows of live episodes.
- *People.* Keyed by email (`upsert_person`). Every name is an alias row. `mention_person` resolves a full name to the single person with that alias, and a first name only to the single person with a full-name alias starting with it (one-word aliases are ignored, so a first name attached once never sticks after a namesake appears); a first-name-only mention with no single match, or a name matching two people, stays an unresolved alias (lesson L12). A full name with no match becomes a person keyed `name:<name>`, for C.5 to merge.
- *Types.* Entity, fact and relation types come from `config/ontology.yaml`; an edge's endpoints must have the types its relation allows.
- *Tasks.* Inserted from the D.5 contract, validated against `config/schema/task.json`, id = sha1(episode + quote), or, when two of one document's tasks share the quote, sha1(episode + quote + "\x1f" + the normalized action) (`task_id`). Allowed transitions and the funnel order (captured → confirmed → ready → done; in_progress counts as ready) are rows seeded by migration 0001, checked on open against the schema's status enum. `funnel()` counts the furthest stage each task ever reached, from its event history.
- *Reads for MCP* (progressive disclosure): `search(text)` returns at most `kg.search_cards` short cards, `get(id)` the entity's facts with quotes and edges (or one fact, edge or task), `source(episode_id)` the transcript path, sha256 and quoted spans. Facts and edges are read in one shape (`FACT_SELECT`, `EDGE_SELECT`), shared with the traversals.
- *Merged entities.* `live_id` follows `merged_into` to the survivor; every lookup and write (`upsert_person`, `mention_person`, `upsert_entity`) lands on it, so a mention after a merge never returns the merged-away id. `add_edge` returns the stored edge with the same episode, relation and quote whose endpoints map to the same live entities, so re-writing an episode after a merge adds no second copy of a repointed edge. Alias rows are indexed for search by alias id (migration 0003), so two aliases with one text keep separate index rows, and a merge moving an alias needs no index change.

**Traversal** (`traverse.py`, `Traverser(store)`), the multi-hop reads behind MCP `neighbors`, `paths`, `timeline`:
- `neighbors(entity_id, *, hops, relations=None, since=None, until=None, as_of=None, types=None, offset=0, through_owner=False)`: entities within `hops` edges, nearest first, then most recently linked (latest `valid_from`), then by name; `types` keeps only those entity types in the answer, `offset` pages it; each with the chain of edges (relation, src → dst, quote, provenance, episode, valid_from/to, state) of a shortest route.
- `paths(src_id, dst_id, *, max_hops, relations=None, as_of=None, through_owner=False)`: up to `kg.traverse.max_paths` shortest routes, no entity repeated, each an ordered edge list.
- `timeline(entity_id, *, since=None, until=None)`: the entity's facts, edges and tasks in time order, superseded rows included and marked `state: superseded` with the reason and replacement; the latest `kg.traverse.max_results` when there are more.
- *What counts:* live episodes and live (unmerged) endpoints; with no time filter, active edges only; with `as_of`, the edges valid then (superseded ones included); with `since`/`until`, the edges valid in the window. Walks are undirected; parallel edges between one pair fold into one hop (`parallel` counts the rest). A merged-away start id is followed to its survivor. No walk steps through the owner's own person node (config `owner.email`, who is in every meeting) unless `through_owner`; the owner can still be a start or an end.
- *Bounded:* hops cut to `kg.traverse.max_hops` (the answer reports hops used), cards to `kg.traverse.max_results`, paths to `kg.traverse.max_paths`, quotes to `kg.traverse.quote_chars`; `truncated` says when a cut happened. A walk running past `kg.traverse.time_limit_ms` is stopped with a `StoreError` (MCP `isError`). Recursive CTEs in shared SQL; each step reads only the edges at its node through the `edge_src_idx` / `edge_dst_idx` indexes (2 hops from a leaf beside a 15k-degree hub in a 150k-edge graph: ~0.2 s); breadth-first reach is deduplicated per (entity, depth), and path enumeration only steps toward entities still within reach of the target.

**Entity resolution** (`resolve.py`, `Resolver(store, state)`), C.5 step 1 pulled forward:
- `candidates()`: same-type pairs sharing an email, a distinctive alias (a person's needs two or more words: a first name alone proves nothing), or names within `kg.er.max_edit_distance` edits (stdlib Levenshtein). Only entities sharing a blocking key (an email, or the first `kg.er.block_chars` letters of a name word) are compared, so it is not all-pairs (4,000 people: 0.7 s, was ~130 s). Certain on a shared email, or on a shared full name between an email-keyed and a name-keyed person when the email-keyed one attended (an alias recorded with that episode) a call the other was named in; anything else needs a typed decision.
- `decide(candidate, ask)`: certain → `same` by rule; else the "same entity?" question (`kg.er.prompt`, schema `kg.er.schema`, role `kg.models.resolve`, `kg.er.context_items` facts and edges per side) through the caller's `ask(role, prompt, schema)`, e.g. `eval.ask.make_ask` over `pipeline.calls.cached_call`. `same` merges, `unsure` is escalated, `different` is left alone.
- `attach_unresolved(run_id)`: a first-name-only mention is attached only when exactly one live person fits; it never becomes an entity (L12).
- `merge(keep_id, drop_id, *, reason, run_id)` and `unmerge(merge_id, *, run_id)`: one transaction each, logged with `State.log_maintenance`. A merge repoints edges, facts, task links and aliases, keeps the dropped name as an alias, sets `merged_into`, and writes the `entity_merge` undo record; merging the same pair again returns that record. Unmerge restores exactly the recorded rows (tested row by row), last-in first-out.
- `run(run_id, ask)`: attach, then decide and merge every candidate; one `entity_resolution` log row per pass. Model decisions are kept in `er_decision` (migration 0004) with a fingerprint of each side's names and email, and a pair whose fingerprints are unchanged is skipped (`skipped` in the summary), so a pass asks only about new or renamed pairs.

**MCP server** (`mcp_server.py`, run by `python -m kg.mcp`): a stdlib-only MCP stdio server (JSON-RPC 2.0, newline-delimited; `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`). The database is opened by `kg.db.connect_readonly` (`mode=ro` URI plus `query_only`, no migration, exact schema match), so answering can never change the graph. Tool arguments are checked against each tool's input schema; malformed JSON, unknown methods and internal errors return JSON-RPC errors and the server keeps reading; logs go to stderr. The tool descriptions tell Claude to chain search → get → neighbors / paths / timeline → source. `tests/fixtures/kg_multihop.json` holds multi-hop questions with their evidence chains: the seed of the C.6 retrieval-QA suite.

**View** (`view.py`, run by `python -m kg.view`): the back end of a Claude Code pane that draws the graph around one entity. Read-only: `kg.db.connect_readonly`, then `Store.search`, `Store.entities_named` and `Traverser.neighbors`, so the walk, its filters and bounds are MCP `neighbors`'s.
- *Commands.* `search <text>`: `{query, results: [{id, name, type}]}`, entity cards only (at most `kg.search_cards`). `neighborhood <entity> [--hops N] [--types T ...] [--relations R ...] [--since D] [--until D] [--as-of D] [--offset N] [--through-owner] [--config F]`: the entity is an id (a merged-away one is followed to its survivor) or an exact name or email (`Store.entities_named`). Answer: `{center, hops, hops_requested, reached, offset, next_offset, truncated, truncated_by, nodes: [{id, name, type, depth, x, y, route_only}], edges: [{id, src, dst, relation, quote, episode, episode_date, valid_from, provenance, state}], svg, alt, text}`.
- *Exit codes.* 0 answer; 1 refused (unknown relation or type, a time that is not ISO-8601, the walk's time limit, a bad config or schema); 2 usage; 3 no database yet; 4 no entity with that id or name; 5 several entities with that name (`candidates` lists them). Every outcome prints exactly one JSON object on stdout, `{"error": ...}` for the non-zero ones; tracebacks go to stderr.
- *Drawing.* Radial rings by depth; each entity sits in a wedge of its parent's (the entity before it on its shortest route) sized by the leaves under it, so neighbours of a node sit near it. Only shortest-route edges are drawn (a tree, one edge per entity). An entity on a route but not in the answer (its type filtered out, or on an earlier page) is drawn faded, `route_only`. Nodes are filled by entity type (`kg.view.palette`, one colour per `config/ontology.yaml` type, checked on start), labels have a halo, and every node and edge has a `<title>` tooltip (name and type; relation, quote, episode date and provenance) with a CSS `:hover` highlight. Same input, byte-identical SVG.
- *Safe to inline.* Names and quotes are XML-escaped; no script, event attribute or external reference, and colours and the font are checked against a strict pattern on start so config text cannot add one. `alt` is a one-sentence summary for screen readers (also the SVG's own `<title>`); `text` is an indented plain-text tree, the terminal fallback.
- *Bounded.* Neighbours are fetched in pages of `kg.traverse.max_results` up to `kg.view.max_nodes`; then the farthest, least recently linked are dropped until the SVG fits `kg.view.svg_max_chars` (the host's 131072). `truncated_by` names the cut(s) and `next_offset` is the `--offset` for the rest. A centre that cannot fit alone is an error, never an over-cap SVG. Quotes are cut to `kg.view.quote_chars`, labels to `kg.view.label_chars`. 40 neighbours: about 21 KB of SVG.

**State** (`state.py`):
- *Runs.* `finish_run` succeeds only if the run processed ≥ 1 item or proved zero eligible (lesson L1), records the backlog, and raises a `run-failed` alert otherwise. Negative counts, or more processed than eligible, raise `ValueError`. `begin_run` fails any run of the same job still marked running (it never finished: the process died or was killed) with the same alert, so a killed run is a failed run and the new one is its retry (D.6); a job runs one at a time.
- *Items.* One per (stage, ref), looked up by id (`item`) or by (stage, ref) (`find`). `begin_item` counts the attempt before the work, so a process-killing item still reaches quarantine after `pipeline.max_attempts`, with one alert naming the fix. `item_failed(..., retry_at=)` stores a next attempt time (migration 0005; the caller picks the backoff, the runner from `pipeline.run.retry_backoff_min`): `eligible` leaves the item out until then, `backlog` still counts it. `requeue` gives it fresh attempts and clears the backoff (`python -m pipeline requeue` also closes its quarantine alert). `undo_attempt` gives back an attempt the machine, not the item, failed (auth, the model unreachable). An item started in `alerts.repeat_item_runs` consecutive runs of its job raises a `repeat-item` alert.
- *Alerts.* Rows with a dedupe key, first/last seen, count, acknowledged. Raising a known key counts and reopens it. `quarantine_digest` moves items quarantined `alerts.quarantine_digest_days` ago into one digest alert, re-raised at most once per period unless new items join.
- *Maintenance.* `log_maintenance` and `record_metric` hold C.5's per-check log and health metrics; `kg/resolve.py` writes `entity_merge` (undo records) and `entity.merged_into`.

## Known gaps

- Attendance is recorded only as an attendee's alias row, and an alias row is written once per (person, name), so only the first call a person attended counts for the shared-full-name rule; later ones fall back to the model decision.
- No nightly job calls `Resolver.run` yet, so nothing binds its `ask` in production; that is the C.5 maintenance job.
- Migrations 0002 and 0003 have no Postgres twin yet (`*.postgres.sql`).
- An empty digest leaves a stale digest alert open.
- A task inserted as `dropped` is missing from the funnel (stream E).
- The viewer draws only shortest-route edges (a tree): an edge between two drawn entities that is on no shortest route (a cross-link, or a parallel edge) is not drawn; `get` lists them.
- The viewer's layout spaces leaves evenly, not by label length, so long labels on a crowded outer ring can touch; the tooltip always has the whole name.
